# 1. Evaluation Overview

This evaluation assesses the project from two complementary perspectives. The production-platform evaluation examined whether encoded zero-width Unicode messages survived documented transfer workflows and whether the original hidden messages could be recovered exactly. The controlled comparative experiment evaluated the effect of optional Hamming error correction when encoded payloads were subjected to specified corruption conditions. The evaluation therefore considers character retention, exact message recovery, detected failures, undetected errors, and the encoded-length overhead introduced by error correction. These measures address different aspects of robustness: character retention describes preservation of the invisible representation, exact recovery describes end-to-end message usability, detected failures indicate whether corruption was rejected safely, and undetected errors indicate whether an incorrect message was returned as if it were valid.

# 2. Interpretation of Production Platform Results

The production results demonstrate that compatibility was strongly dependent on the tested platform and operation. Notepad++, Telegram Web, and Google Chrome Browser Console each achieved exact recovery in all 24 completed trials. Completed Discord trials also achieved 21/21 exact recoveries, or 100% among the trials that reached transmission and produced analyzable results. These outcomes show that the baseline codec can function reliably when the tested workflow preserves the project’s zero-width characters and returns the encoded text without a damaging transformation. They should be interpreted as workflow-specific observations rather than universal compatibility guarantees.

The remaining platforms produced substantially different outcomes. Microsoft Outlook completed all 24 trials and recovered 19 messages exactly, for a 79.17% exact-recovery rate. Its aggregate character retention was higher, at 90.27%, demonstrating that preservation of most invisible characters does not necessarily preserve every byte, separator, or frame relationship required for exact decoding. Gmail retained a small fraction of the encoded characters, with an aggregate retention of 5.41%, but produced no exact recoveries. Microsoft Word retained none of the measured zero-width characters and likewise produced no exact recoveries. These results support evaluating both character-level retention and message-level recovery: the former can indicate partial preservation, while the latter determines whether the hidden message is usable without reconstruction or guesswork.

The Discord result requires separate accounting. Three LA02 repetitions were blocked before transmission because the unchanged encoded payload exceeded the standard Discord message-size limit. They were not failed decoder trials and were excluded from the completed-trial denominator. Consequently, the result is 21 exact recoveries from 21 completed Discord trials, alongside three blocked planned trials. More generally, the production evidence establishes differences among the tested application workflows, but it does not establish a single technical cause for every platform’s behavior. The experiments were limited to the recorded application versions, transfer procedures, eight-message production corpus, and documented operating conditions.

# 3. Evaluation of Baseline vs. Hamming

The controlled comparative experiment measured a clear improvement in overall recovery when the Hamming configuration was enabled. Baseline recovered 12 of 60 trials, or 20%, whereas Hamming recovered 24 of 60 trials, or 40%. Both methods recovered all 12 trials with no corruption, so the difference was not attributable to ordinary encoding and decoding in the absence of damage. Instead, it arose from Hamming’s performance under the tested single-bit corruption condition: Baseline recovered 0/12 of those trials, while Hamming recovered 12/12.

The improvement was specific to the tested bit-substitution case. Neither method recovered any of the 12 double-bit-corruption trials, the 12 trials with approximately 1% deletion, or the 12 trials with approximately 5% deletion. The Hamming result is therefore consistent with the implementation’s intended protection against supported single-bit alterations, but it does not demonstrate protection against symbol deletion or against multiple altered bits in a codeword. The experiment used deterministic corruption schedules and a limited four-message corpus, so its results should not be generalized to arbitrary platform transformations or all possible corruption patterns.

All 84 unsuccessful comparative trials were classified as detected failures, and no trial produced an undetected incorrect message. This is an important safety property of the tested configuration: unsuccessful decoding was preferable to returning a nonexact message as successful plaintext. However, detection does not restore the hidden message. Hamming therefore improved recovery in the tested single-bit condition while leaving deletion-related loss unresolved. That improvement also required additional representation length. Across the four comparative messages, Hamming overhead ranged from 55.70% to 57.24% relative to Baseline. The measured trade-off is consequently between increased encoded size and improved recovery for a particular class of bit corruption, not between overhead and general immunity to data loss.

# 4. Project Strengths and Limitations

One strength of the project is that it evaluated robustness at multiple levels rather than relying on a single success measure. The production study recorded both zero-width character retention and exact message recovery, making it possible to distinguish partial preservation from usable end-to-end recovery. The comparative study separately recorded successful recoveries, detected failures, and undetected errors. This classification prevents a safely rejected damaged payload from being treated as equivalent to a recovered message and makes the absence of undetected errors visible in the reported results.

The experimental organization also supports reproducibility. Production testing used a frozen eight-message corpus, seven approved platform-operation combinations, and three repetitions per message, for 168 planned trials. The comparative experiment used four defined messages, two encoding methods, five corruption conditions, and three deterministic repetitions per combination, for 120 trial records. Individual JSON records, consolidated CSV files, documented procedures, and chart data preserve the inputs and aggregate calculations used in the Results section. The project also includes baseline and optional Hamming encoding modes, documented decoder validation, and a reported final regression run of 83 tests and 546 subtests with no reported failures. The automated regression result is software-validation evidence, not an additional production or comparative experiment.

The principal limitations concern scope and generalizability. The production corpus contained eight frozen messages and the comparative corpus contained four, so repeated trials increase the number of observations without providing an equivalent number of unique message contents. The tested application versions and transfer workflows also represent specific operating conditions. An application update, different input field, different copy-and-paste path, or different operating system behavior could produce a different outcome. The production findings therefore demonstrate compatibility characteristics for the documented workflows, not for every version or use of the tested applications.

The comparative corruption model is similarly limited. It tested no corruption, specified single-bit and double-bit alterations, and approximately 1% and 5% deletion according to the documented deterministic schedules. Real platform transformations may involve character-class filtering, reordering, normalization, truncation, insertion, or combinations of these effects. The tested Hamming configuration did not recover the double-bit or deletion trials, and its substantial 55.70%–57.24% measured overhead may restrict practical use for long messages or platforms with strict message-size limits. The blocked Discord trials illustrate that payload length can itself prevent a workflow from being tested, even before decoder performance is measured.

Finally, zero-width encoding is not a confidentiality mechanism. The codec hides data from ordinary visual inspection, but it does not encrypt the hidden message or provide access control, authenticity, or non-repudiation. Anyone who knows the character mapping and frame format may inspect or decode the payload. The project’s results therefore support an assessment of preservation and error handling, not a claim of secure communication. These limitations are material because they define where the measured robustness results can reasonably be applied and where additional protection or testing would be required.

# 5. Future Improvements

Future work should first expand the evidence base. Additional messages with varied lengths, languages, scripts, punctuation, and Unicode combinations would test whether the observed retention and recovery patterns depend on corpus composition. More repetitions alone would not replace message diversity, because repeated trials of the same encoded content do not represent independent coverage of different payload structures. The comparative experiment could likewise be expanded with additional message sizes and corruption locations while preserving deterministic metadata so that results remain reproducible.

The production study could be extended to additional application versions, operating systems, input fields, and transfer workflows. Repeating the same protocol after application updates would help determine whether compatibility is stable over time. Additional workflows should continue to record the exact operation, application and system versions, retrieved text, analyzer output, and evidence paths. This would allow future changes in platform behavior to be distinguished from differences in testing procedure.

Improving recovery from deletion corruption is another important direction. The current Hamming configuration addresses supported bit substitutions, but deletion of zero-width symbols can destroy codeword alignment and cannot be corrected by the tested configuration. Proposed approaches include synchronization markers, interleaving, redundancy designed for erasures, or alternative error-correction schemes that can identify and recover from missing symbols. Any such approach would require controlled evaluation against both isolated and clustered deletions, as well as explicit checks that added synchronization data does not create unacceptable false positives or message-size growth.

The encoded-length trade-off should also be investigated. Future implementations could evaluate more compact redundancy, adaptive protection based on message length or expected corruption, or alternative codes with different correction and overhead characteristics. These are proposed design directions, not completed project features. Their value would need to be measured using the same recovery, detected-failure, undetected-error, and length-overhead metrics used in the current comparison.

Further automated testing and reproducibility tooling could improve maintenance and confidence in future experiments. Possible additions include automated checks for CSV-to-chart consistency, validation that all trial evidence paths exist, regression tests for blocked-trial accounting, and repeatable analysis commands that produce summaries directly from immutable JSON records. Finally, zero-width character detection and filtering should be investigated as a separate security and deployment concern. Understanding how applications, scanners, or moderation systems detect invisible payloads would complement the current robustness results without conflating message preservation with confidentiality.
